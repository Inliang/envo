## 0. 一句话结论

Envo 是**单页 SPA，四个 Tab 共用一个 URL**，sitemap 只有 1 条 `<url>`，搜索引擎能抓到的静态正文目前**只有 title 里那十来个字符**。所以本次内容工作的重心不是"多写几段文案"，而是**把标题、描述、结构化数据、社交卡片这四块静态文本一次写对**，再补一段 `<noscript>` 兜底正文；界面微文案则做克制的准确性修正——重点不是让它更好看，而是让它**不再骗人**。

> **本文档已与 T1-ARCH 的 `site-spec.md` 冻结契约全面对齐**（TDK / OG / theme_color / JSON-LD 类型与属性值 / 静态资源命名 / 移动端非转化定位）。对齐状态见第 12 节。凡 T1 已冻结的文本，本文档逐字采用，不另立第二套。

## 1. 内容现状审计

### 1.2 视图一：信封编辑（`EnvelopeEditor.tsx`）

现有文案：寄件人信息（姓名 / 地址 / 电话 / 邮编）→ 收件人信息（姓名 / 单位 / 公司 / 地址 / 电话 / 邮编，地址框 placeholder「输入地址关键词自动联想…」）→ 信封设置（规格下拉，optgroup「── 国内信封 ──」「── 国际信封 ──」、自定义宽高、显示寄件人地址开关）→ 操作按钮（打印信封 / 导出 PDF / 存地址簿 / 清空）→ 实时预览 + 尺寸标签 + 快捷地址簿。

问题：

1. **字段命名与真实用途错位**（⚠️ **本条结论已被用户裁决推翻，见 §7.2 #4**）：第一个字段标「姓名」（`Address.name`），第二个标「单位 / 公司」（`Address.recipient`）。打印文件名用 `recipient.recipient`、打印历史主行也显示 `recipient.recipient`，我据此判断"这一栏是信封主展示行、个人用户会留空导致主行空白"——**这个判断是错的**：信封正面主展示行的实际取值是 `recipient.recipient || recipient.name`（`envelopeCanvas.ts:180`、`:317`），**个人用户填了姓名，主行就有值**，不依赖这一栏。文案层不需要为代码已兜底的问题做引导。
2. **校验提示与字段标签打架**：提示写「请填写收件人和地址」，但页面上根本没有叫「收件人」的输入框。
3. **按钮缺宾语**：「存地址簿」「清空」。「清空」实际只清收件人（`clearForm` 不碰 sender），文案没说清范围。
4. **「+ 地址簿」读作"新建地址簿"**，实际是跳转地址簿去挑已有地址。
5. **未配置高德 Key 时零反馈**：`getAmapKey()` 为空时直接静默返回，用户输入后什么也不发生，会以为功能坏了。
6. **规格下拉用了制表符短横** `── 国内信封 ──`，部分字体/系统下渲染成方块或断行。
7. **Canvas 无文本替代**：`<canvas>` 没有 `role`/`aria-label`/回退内容，屏幕阅读器完全读不到预览。
8. **「显示寄件人地址」开关是无语义 `<button>`**，没有 `role="switch"` 与 `aria-checked`。
9. **提示条（msg）无 live region**，成功/失败提示读屏用户收不到。
10. **界面无任何"模板/尺寸/免费"字样**，承接不了「信封打印模板」「信封尺寸」这类搜索意图。

### 1.3 视图二：地址簿（`AddressBook.tsx`）

现有文案：地址簿（h2）→ 导入 / 导出Excel / + 添加地址 → 导入预览（共解析 N 条记录、（N 条跳过）、没有可导入的有效记录、确认导入 N 条、取消）→ 新建表单（姓名 * / 单位 / 公司 / 地址 * / 邮编（如 100000）/ 电话 / 选择标签）→ 搜索地址... + 标签筛选（全部 / 家 / 公司 / 亲友 / 其他）→ 全选 / 取消全选 / 批量打印（N）→ 卡片（姓名、单位、标签、地址、邮编: x、电话: x / 打印此信封 / 编辑 / 删除）。

问题：

1. **「打印此信封」名不副实**：点击只是 `setCurrentRecipient` + 跳到编辑页，**不会真的打印**。文案承诺了做不到的事，是最需要修的一条。
2. **「导出Excel」缺空格**，与编辑器里的「导出 PDF」写法不一致。
3. **搜索 placeholder 只写"地址"**，实际代码按 `name / recipient / address` 三个字段过滤，用户会以为搜不到姓名。
4. **空状态无引导**：「地址簿为空，点击上方按钮添加」只提了一个入口（还有导入），且没说按钮叫什么名字；「无匹配结果」更是四个字砸在那儿，没给下一步。
5. **删除确认框不含姓名**：`确定删除此地址？`——多条地址时不知道要删哪条，删完也无撤销。
6. **省略号不统一**：「搜索地址...」「正在解析文件...」用半角三点，编辑器里用的是「…」。
7. **中英文之间/冒号用法不统一**：`邮编: xxx`、`导出Excel`、`导出JSON`（Settings）。

### 1.4 视图三：打印历史（`PrintHistory.tsx`）

现有文案：打印历史（h2）→ 📥 导出Excel / 清空历史 → 筛选（全部 / 今天 / 本周 / 本月）→ 记录行（收件人、打印或 PDF 标签、地址、时间 + `{size}规格`、重新打印 / 删除）→ 空状态（暂无打印记录 / 当前筛选条件下无记录）。

问题：

1. **「本周」「本月」与代码行为不符**：`week` 是 `now.getDate() - 7`（过去 7 天滚动窗口），`month` 是 `setMonth(-1)`（过去 30 天滚动窗口），**不是自然周/自然月**。周一早上打开会看不到上周五的记录。
2. **「重新打印」名不副实**：点击后回到编辑页预填，不直接打印。
3. **空状态无引导**：「暂无打印记录」没告诉用户记录从哪来。
4. **删除无二次确认**，与地址簿的删除有确认形成行为不一致（属行为项，列入决策）。
5. `{size}规格` 中英文粘连，且只显示规格代码（如 `DL`），用户看不出是多大。

### 1.5 视图四：设置（`Settings.tsx`）

现有文案：默认寄件人（姓名 / 电话 / 地址 / 邮编，仅 placeholder 无 label）→ 高德地图 API Key（说明文案、去申请 Key、显示/隐藏、保存 / 已保存、Key 已加密保存）→ 数据管理（导出地址簿 / 导出打印历史 / 导出所有数据 / 导入数据备份，按钮为「导出」「导出」「导出JSON」「导入」）→ 关于（信封打印助手 v1.0.0 / 支持 DL/C5/C4/C6 标准信封规格及自定义尺寸 / 所有数据存储于浏览器本地，不会上传至任何服务器 / 地址簿: N 条、打印历史: N 条）。

问题：

1. **版本号过期**：v1.0.0，本次交付 v1.0.1（页脚同样过期）。
2. **规格说明漏了一半**：实际支持 ZL / DL / C5 / C4（国内）+ B6 / C6（国际）+ 自定义共 7 项，文案只写了 DL/C5/C4/C6，**漏了 ZL 和 B6**，也没说清国内/国际分类。README 同样漏。
3. **三个按钮都叫「导出」**：数据管理里两个「导出」+ 一个「导出JSON」，屏幕阅读器列出按钮时无法区分。
4. **「保存」缺宾语**：页面上有多组输入框，单独一个「保存」不知道保存的是 Key。
5. **「AES 加密存储」是技术黑话**，没说清"存在哪儿"。
6. **导入结果用原生 `alert`**：「数据导入成功」没说导入了什么；「导入失败：文件格式不正确」没说需要什么格式。
7. **整页表单只有 placeholder 没有 label**，屏幕阅读器与自动填充都受影响。
8. **「显示 / 隐藏」密码切换按钮**无 `aria-label`/`aria-pressed`，读屏时无法与 Key 输入框关联。

### 2.2 长度核算（已实测，双双达标）

| 项 | 长度核算 | 结论 |
|---|---|---|
| title | 汉字 17 + 标点 1 + 拉丁 23 = **59 半角单位**（约 490px） | ≤ 30 字含品牌词 ✓；Google 显示上限约 600px，**不会被截断** ✓ |
| description | 汉字 59 + 标点 8 + 拉丁 22 = **67 字 / 156 半角单位** | 落在 60–80 字区间 ✓；宽度压在 Google 约 160 单位截断线**以内** ✓ |
| keywords | 8 个词，无重复 | 只放真正对应的词，不放「信封」「打印」这类电商/百科垄断的泛词 |

**为什么这版定稿必须压过架构侧初稿**（三条，均为可验证的事实）：

1. **初稿宣称了一个失效功能**：初稿写「地址智能联想**自动补全邮编**」。但高德 v3 `inputtips` 官方**根本不返回 `postcode`**，代码是拿 11 位 `towncode`（乡镇行政编码）冒充邮编（`EnvelopeEditor.tsx:132`，R5）。邮编填错会导致**信件分拣错误，实体不可逆**。对外宣称这个功能属**虚假承诺**，必须撤。**本定稿通篇不出现"邮编自动补全"。**
2. **初稿的规格枚举是错的**：初稿写「DL/C5/C4/**C6**」。按 `src/store/types.ts` 的 `ENVELOPE_SIZES`，国内主力规格是 **ZL/DL/C5/C4**；C6 与 B6 是**国际规格，不得写成国产**（§5.5）。本定稿写 `ZL/DL/C5/C4`。
3. **初稿混入了内部实现术语**：「Canvas 实时预览」里的 Canvas 是实现技术，用户在搜索结果里看到无感，占掉了宝贵的字数。本定稿改为用户语言「实时预览排版」。

### 2.3 补充 head 标签

```html
<meta name="robots" content="index,follow,max-image-preview:large" />
<meta name="theme-color" content="#0D9488" />
<meta name="format-detection" content="telephone=no" />
```

> `theme-color` 取 `#0D9488`，与 `site.webmanifest` 的 `theme_color` 一致（架构侧原值，两侧无冲突）。
> `canonical` 取 `https://inliang.github.io/envo/`（**带尾斜杠**，GitHub Pages 对 `/envo` 会 301 到 `/envo/`），架构侧原值，两侧一致。

**`meta name="keywords"`：本次不加。** 理由：T1 冻结的 `<head>` 目标形态里没有这一条，Google 已完全忽略该标签；为保持 head 与契约逐字一致，不额外插入。若后续确认要照顾百度，用这一版（不在契约内，属可选）：
`信封打印,信封打印模板,在线打印信封,信封尺寸,批量打印信封,信封地址打印,导出PDF,地址簿`

## 4. canonical 与多语言

### 4.1 canonical（定稿）

```html
<link rel="canonical" href="https://inliang.github.io/envo/" />
```

- 全站只有一个 URL，canonical 指向自身即可。
- **必须带尾斜杠**：GitHub Pages 对 `/envo` 会 301 到 `/envo/`，canonical 写带斜杠的形态避免多一次跳转判断。
- 四个 Tab 不产生独立 URL，**不需要**各自 canonical，也不需要 `?tab=` 之类的参数处理。

### 4.2 hreflang：**明确不加**

结论：不需要。

理由（三条，任一成立即足够）：

1. 站点只有 `zh-CN` 一种语言版本，`<html lang="zh-CN">`，不存在需要互指的第二版本。没有对照页的 hreflang 是无效标记。
2. hreflang 的语义是"这些 URL 是同一内容的不同语言/地区版本"，且要求**双向互指**。单语言站加 `hreflang="zh-CN"` 指向自己，Google 会忽略，还白白增加 head 体积。
3. 同理也不需要 `x-default`。

**未来触发条件**（写成规则，便于后续判断）：只有当出现英文版 `https://inliang.github.io/envo/en/` 之类独立 URL 时，才在两页同时加上 `zh-CN` / `en` / `x-default` 三组互指标记。

| 字段 | 处理 | 原因 |

### 7.5.1 Key 说明文案修订（R7 专项 · 现状 → 建议 → 理由）

| | |
|---|---|
| **现状** | `用于地址智能联想。Key 将使用 AES 加密存储。` |
| **建议** | **主推（两行，推荐）**<br>第 1 行：`用于地址智能联想，输入地址关键词时自动提示候选地址。Key 只存在这台设备的浏览器里，不会上传服务器，存一次下次打开就不用重填。`<br>第 2 行（视觉上弱化，小字/浅色）：`注意：这只是本地保存，不是加密保险箱。请勿填写高价值 Key，建议在高德控制台设置每日调用上限。` |
| **理由** | 见下方四条 |

**理由（拆开说）**

1. **不谎报安全等级**：`src/utils/encryption.ts` 里 `SECRET = 'envelope-printer-secret-2024'` 硬编码在前端源码，用户打开 DevTools 就能看到，加密**可逆**。原文「AES 加密存储」把"混淆级"说成了"安全级"，会诱导用户填入高价值 Key——这是信任问题，不是措辞问题。
2. **说明存 Key 是为了方便**：原文只说了"用于联想"，没说"为什么要存"。补上「存一次下次打开就不用重填」，用户才知道这是**便利功能**而非安全承诺，也就自然理解"不填也能用"。
3. **说清数据不上传**：`Key 只存在这台设备的浏览器里，不会上传服务器` —— 这是真实且不打折的承诺，也是这个工具最值得说的优点，应该讲。
4. **给可执行的自保动作**：`请勿填写高价值 Key` + `在高德控制台设置每日调用上限`。与其含糊地说"请注意安全"，不如告诉用户具体怎么做。

**备选（一行紧凑版，若卡片空间紧张）**

> `用于地址智能联想，输入关键词自动提示候选地址。Key 仅保存在本机浏览器、不会上传，存一次下次免填；它不是加密保险箱，请勿填写高价值 Key，建议在高德控制台设置每日调用上限。`

> ⚠️ **本节原稿里的「自动补全并填邮编」已全部撤下**（R5，理由同 §7.2 #11）。Key 说明只承诺确实成立的那一半：联想候选地址。邮编一律由用户手填。

### 8.3 主导航（四个 Tab）

> **⚠️ 结论已改。我原先建议的 `role="tablist"` 方案被驳回并撤回**，采纳视觉设计师的异议：ARIA Tabs 模式要求配套**左右键键盘漫游 + `aria-controls` + 面板 `hidden` 三件套**；只做 `role="tablist"` / `role="tab"` / `aria-selected` 这半套，读屏用户会被告知"这是一个标签页"却切换不了，**比完全不做更糟**。而本项目四视图是整页互斥切换，语义上就是**站内导航**，不是标签页。

**正确做法**

```html
<nav aria-label="主导航">
  <button aria-current="page">信封编辑</button>
  <button>地址簿</button>
  <button>打印历史</button>
  <button>设置</button>
</nav>
```

| 项 | 做法 |
|---|---|
| 导航容器 | `<nav aria-label="主导航">` |
| 当前选中项 | `aria-current="page"`（仅当前项有，其余不加） |
| **明确不写** | ❌ `role="tablist"` ❌ `role="tab"` ❌ `aria-selected` ❌ `aria-controls` ❌ `role="tabpanel"` |

**为什么这样反而更好**：`<nav>` + `aria-current="page"` 让读屏直接播报"主导航，信封编辑，当前页面"，语义准确、零维护成本、不需要额外实现键盘漫游。四个 `<button>` 本身可 Tab 聚焦、可回车触发，键盘可达性已经是完整的。

### 8.4 Canvas 预览

`<canvas>` 加 `role="img"` 与动态 `aria-label`，并在标签内放回退文本：

- `aria-label` 示例：`信封排版预览，{规格}（{宽}×{高} 毫米），收件人 {姓名}，地址 {地址}`

## 12. 交付小结

### 文案关键取舍

1. **放弃"多写文案换排名"，选择"把静态 head 写对"。** sitemap 只有 1 条 URL、四个 Tab 不可单独索引——title、description、OG、JSON-LD 这四块是唯一确定能被抓到的东西。其余界面文案的 SEO 价值接近于零，它们的价值在于**别骗用户**（「打印此信封」不打印、「本周」不是本周）。
2. **放弃「信封打印模板」这个词。** 站内没有可下载的模板文件，只有规格选择。为了一个词去承诺不存在的东西，会同时伤害转化和信任。
3. **放弃编造评分与作者做富摘要。** 没有真实评分就不写 `aggregateRating`，没有署名实体就整段删掉 `author`——宁可字段少，不骗搜索引擎。
4. **微文案只改"说错的"和"没说的"，不改"说得好不好的"。** 41 条中原定 25 条必改（#4 推翻后实际执行 24 条），全部集中在**文案与行为不符**（「打印此信封」不打印、「重新打印」不打印、「本周」不是本周）、**安全等级表述错误**（「AES 加密存储」其实是前端可逆的混淆）、**功能承诺落空**（「自动补全邮编」实际拿 towncode 冒充，会填错）、**信息过期**（v1.0.0、漏了 ZL/B6 两种规格）、**空状态无引导**五类硬伤上；润色类全部标为可选。
5. **有一条我被推翻了，记录在案**：#4「单位 / 公司 → 收件人 / 单位」。我当时的理由是"这栏是信封主展示行，个人用户留空会导致主行空白"——**这个判断是错的**。信封正面主展示行的实际取值是 `recipient.recipient || recipient.name`（`envelopeCanvas.ts:180`、`:317`），个人用户填了姓名主行就有值。我误把"文件名/历史主行取值"当成了"信封正面取值"。**用文案去引导一个代码已兜底的问题，方向本身就是错的**——这是本次内容侧最有价值的一条教训。
6. **移动端 CTA 不追打印。** 手机打不了 220×110mm 的信封，任何"立即打印"的话术在移动端都是空头支票。移动端只引导两件真能做成的事：去桌面端打、先把地址存进地址簿。
7. **全站撤下「邮编自动补全」。** 这是本次最不该对外说的一句话——高德 `inputtips` 官方不返回 `postcode`，代码用 11 位 `towncode` 冒充，**填错会导致信件分拣错误、实体不可逆**。TDK、OG、JSON-LD `featureList`、地址框 placeholder、Key 说明文案，五处全部清干净，一处不留。
8. **可见层做减法，语义层靠 `aria-label` 补。** B9 与 #4 的裁决指向同一个原则：屏幕上重复出现「收件人」（卡片标题 + label + placeholder）是噪音，读屏用户需要的信息用 `aria-label` 给就够了，不必牺牲视觉去迁就它。
